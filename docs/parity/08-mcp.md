# 08 MCP server

Present only when `mcp.enabled` is true (CFG-13). Built behind the cargo feature `mcp`. Each Route can be exposed as an MCP tool that calls the Upstream Service.

Rows MCP-15 and MCP-16 keep reference quirks on purpose (approved under Q17 row 11).

## MCP-02 (Deviation D13): rmcp 3.11 compared with the TypeScript SDK 1.32

`McpEndpoint` uses `rmcp`'s `StreamableHttpService` with `legacy_session_mode = false`, `json_response = false`, host checking disabled and `NeverSessionManager`. Two settings bring it closer to the reference: `initialize` negotiates within the reference's version list (`supported_protocol_versions`), and unknown methods answer `Method not found`. Everything else below is `rmcp`'s own behaviour, accepted as Deviation D13 (approved 2026-11-18) and pinned by `gateway_endpoints::mcp::d13_mcp_transport_follows_rmcp` (through the served gateway) and `mcp::tests::endpoint_transport_behaviour_of_rmcp` (the endpoint alone), so an `rmcp` upgrade that changes any of it fails a test. The reference's side is checked by `mcp::mcp_02_transport_reference_only`. Same in both: `initialize` result fields and negotiated versions, `ping`, `tools/list` and `tools/call` results, no session id, 202 for a notification, SSE for a request, `content-type` parameters accepted.

| Exchange | Reference (TypeScript SDK) | rmcp |
|---|---|---|
| SSE framing and headers | `event: message` line before each `data:`; `cache-control: no-cache, no-transform`, `connection: keep-alive` | `data:` only; `cache-control: no-cache` |
| Batch (JSON array) | Accepted: one event per response; 202 when it holds no request, also `[]` | 415, text `fail to deserialize request body unrecognized JSON-RPC message` |
| JSON-RPC response from the client | 202, no body | 400 `{"jsonrpc":"2.0","error":{"code":-32600,"message":"stateless server does not accept JSON-RPC responses"}}` |
| Malformed JSON, empty body | 400 `application/json`, `-32700` `Parse error: Invalid JSON`, `id: null` | 415, no content type, text `fail to deserialize request body <serde error>` |
| Valid JSON that is not JSON-RPC (`{"foo":1}`, `"jsonrpc":"1.0"`, `"id":null`) | 400, `-32700` `Parse error: Invalid JSON-RPC message` | 415, text as above |
| `Accept` without both media types | 406, JSON-RPC body `-32000` `Not Acceptable: …` | 406, the same message as plain text |
| Content type not JSON | 415, JSON-RPC body `-32000` `Unsupported Media Type: …` | 415, the same message as plain text |
| Unsupported `mcp-protocol-version` | 400, JSON-RPC body `Bad Request: Unsupported protocol version: <v> (supported versions: …)` | 400, text `Bad Request: Unsupported MCP-Protocol-Version: <v>` |
| `mcp-protocol-version: 2024-10-07` | Accepted | 400 (rmcp validates the header against its own known versions) |
| `mcp-protocol-version: 2026-07-28` | 400 unsupported version | 400 `-32020` `missing required Mcp-Method header` (rmcp knows this version) |
| Method of a capability the server lacks (`resources/list`) | `-32601` `Method not found` | `-32601` with the method name as message |
| Invalid `tools/call` params (no `name`, array `arguments`) | `-32603` with the SDK's validation text | `-32601` `Method not found` |
| Body larger than 4 MiB, batch of more than 100 messages | 413 JSON-RPC body `Payload Too Large: Request body must not exceed 4194304 bytes`; 400 `-32600` for the batch (read from the SDK, not run) | 413, text `Payload Too Large: request body exceeds 4194304 bytes`; batches refused anyway |

Closing these gaps would need either a front layer that answers the transport-level cases itself (batches, client responses, the HTTP-level error bodies) or changes in `rmcp`. Deviation D13 accepts them instead.
